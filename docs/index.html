Napkin math gets this wrong three ways

1. Cache tokens are not input tokens

A 5-minute cache write costs 1.25× base input. A 1-hour write costs 2×. A cache read costs 0.1×. Claude Code uses all three — and on real sessions cache traffic is routinely over 90% of total token volume. Price it as plain input and you can be out by an order of magnitude, in either direction.

2. The transcripts repeat themselves

The same API response is written to the JSONL log several times. On measured data that is roughly 70% duplicate rows. Add up every line and you inflate your own bill. ccost de-duplicates on the response id.

3. Some charges aren't tokens

Web search bills $10 per 1,000 searches on top of tokens. Fast mode reprices Opus 5 at $10/$50. inference_geo: "us" puts a 1.1× multiplier on everything.

The cache break-even test

A 1-hour cache write costs 2× base input; a read costs 0.1×. Writing once and reading it N times costs 2 + 0.1N, versus N + 1 uncached. Caching only wins once N ≥ 2.

If your reads-per-write ratio sits below that line, prompt caching is actively costing you money — and nothing in your tooling will say so. ccost computes the counterfactual directly: what you actually paid, against what the identical traffic would have cost with caching off.
